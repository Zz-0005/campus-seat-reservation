# 产品演示脚本（8 分钟）

面向周日产品展示。目标不是"把功能点一遍"，而是让评审看到**需求 → 实现 → 验证**这条链条立得住。

| 项目 | 说明 |
| --- | --- |
| 时长 | 主体 8 分钟 + 答疑 5 分钟 |
| 演示环境 | 一台笔记本，浏览器开两个窗口（普通 + 无痕），一个终端 |
| 演示素材 | 本地运行的 `python server.py`；终端里的 `python tools/race_demo.py` |
| 兜底 | 见文末「出问题怎么办」 |

## 演示前 5 分钟准备

```bash
# 1. 干净数据，避免上一轮预约残留影响演示
rm -f data/seats.db          # Windows: del data\seats.db

# 2. 启动服务
python server.py

# 3. 浏览器开两个窗口
#    窗口 A（普通）  http://127.0.0.1:8000   身份：2024001 / 林小雨
#    窗口 B（无痕）  http://127.0.0.1:8000   身份：2024002 / 陈默

# 4. 终端准备好，等下要用
```

提前把两个窗口都切到同一间自习室、同一天（明天），停在这一屏，别在台上现找。

## 分镜

### ① 开场：一句话讲清产品（40 秒）

> 这是一个校园自习座位预约系统。场景很具体：图书馆开馆前，同学在门口排队抢座位，靠自觉和便利贴；我们的产品让这个过程在手机上 10 秒完成，并且保证**同一个人同一时段只能被一个人约到**。
>
> 技术上它不是玩具：服务端零第三方依赖，14 个时段 × 146 个座位，并发抢座时只有一个人成功——这一点我一会儿用 16 个并发请求现场验证。

**动作**：展示首页，停留 2 秒让大家看清座位图配色。

```text
[截图] docs/images/shot-desktop-booking.png
```

### ② 主流程：切换自习室 + 选时段预约（90 秒）

**操作**：点顶部不同自习室标签 → 点日期条切到明天 → 点一个绿色座位 → 点"4 小时"快捷按钮 → 确认预约。

**讲解词要点**：

- 显示层：绿色空闲、橙色部分可约、红色已约满、蓝框是我的预约——一眼看出能不能约。
- 交互层：点座位右侧列出该座位当天 14 个时段，可点起止，也可以快捷选 1/2/4 小时。
- 确认后座位立刻变红，我的预约列表出现一条"未开始"。

**预期现象**：座位由绿变红（或变"部分可约"橙），列表计数 +1。

### ③ 冲突与互斥：这是产品的核心（90 秒）

**操作**：窗口 B 用另一个学号，去点刚才那个座位刚被占的时段。

**讲解词**：

> 已占用的时段在这里是不可点的，但这只是体验层的拦截。真正的保障在数据库：占用明细表的主键是「座位 + 日期 + 时段」，一次预约 N 小时就是一个事务写 N 行，任意一行冲突整笔回滚。所以即使绕过界面直接调接口，也拿不到同一个座位。

**动作**：窗口 B 界面上看不到那个时段可选 → 说明前端拦截；接着切到终端（下一镜）说明后端拦截。

### ④ 现场证明并发唯一（90 秒）

**操作**：终端执行

```bash
python tools/race_demo.py --threads 16 --room 3
```

**预期输出**：

```
目标：A201 自习室 自习室 A-01 座位，2026-10-26 的 16:00-17:00
并发：16 个线程同时提交预约

  线程 00 → 201 OK
  线程 01 → 409 SLOT_TAKEN
  ...
结果：成功 1 个，冲突被拒 15 个，其他 0 个
核对数据库：该时段已被占用
结论：并发控制正确，只有一个同学预约成功
```

**讲解词**：

> 这 16 个请求是同时发出的，绕过了前端，直接打接口。结果是一个 201、十五个 409，数据库里这个时段只有一条占用。这条不是靠锁住整个服务实现的，是靠数据库的唯一约束——所以多进程部署也成立。

### ⑤ 取消预约：状态回落（50 秒）

**操作**：窗口 A 在"我的预约"里点"取消预约" → 座位变回可约 → 窗口 B 立刻能约到（5 秒轮询内自动刷新）。

**讲解词**：

> 只有本人、只有还没开始的预约能取消，越权返回 403，重复取消返回 400。取消后时段立刻释放，另一个窗口不用刷新，5 秒内自己就变绿了。

### ⑥ 这一轮是怎么迭代出来的（120 秒）

**操作**：打开 GitHub 仓库，按顺序走一遍：PRD → PR → Issue → 修复 PR → Release。

**讲解词**：

> 产品不是一次写完的。第一版按 PRD v1.0 交付后，两位"用户"实际去用，提交了 5 个 Issue——手机窄屏座位图横向溢出、切到后台还在每 5 秒轮询、关页面时服务端打印整段异常堆栈、favicon 404，还有一个需求遗漏：单次可以约满 14 小时，等于一个人占掉一整天的座位。
>
> 前四个我修复并让用户重新验收，第五个涉及业务规则（上限多少、要不要分高峰），我没有拍脑袋改，而是记进 PRD 13.4 作为待定项进 v1.2。这些在仓库里都能翻到：Issue 里有产品定性、研发根因回复、用户验收结论。

**动作**：依次展示 `Issue #2` → `PR #7` → `Releases: v1.1.0` → `docs/PRD-...md` 的修订记录。

### ⑦ 结尾：一句话收口（20 秒）

> 所以这个项目交付的不只是一个能跑的页面，还有一份真正指导过开发的 PRD、可复现的并发证据、以及一轮真实的用户反馈闭环。手机上也能用——这是 v1.1.0 修的。

## 出问题怎么办

| 状况 | 处理 |
| --- | --- |
| 端口 8000 被占用 | 换端口启动：`python server.py --port 8080`，浏览器地址同步改 |
| 演示数据乱了 | 停服务、删 `data/seats.db`、重启，会自动重建 4 间自习室与演示预约 |
| 目标座位全被占满 | 换一间自习室，或切到更靠后的日期（可预约今天起 7 天） |
| 并发脚本报连不上 | 确认服务端在同端口运行；脚本可加 `--base http://127.0.0.1:8080` |
| 网络/环境异常，页面打不开 | 直接展示 `docs/images/` 里的截图，并跑 `python tests/test_booking.py` 用 43 项检查兜底 |
| 被问到没做的东西 | 直接说"这版没做，已记在 PRD 13.3 候选需求里"，不要现场编 |

## 现场最容易踩的三个坑

1. **别在台上现启动服务**：提前启动好，让日志里有数据，切换窗口更顺。
2. **两个窗口要真正独立**：无痕窗口才不会被同一个 localStorage 身份串掉。
3. **演示前不要动数据库路径**：`--db` 参数一旦改过，之前的演示数据就对不上了。

## 时间不够时的压缩版（4 分钟）

砍掉 ② 的完整流程与 ⑤，只留：开场（40 秒）→ 预约一个座位（40 秒）→ 并发脚本（90 秒）→ 迭代故事（60 秒）→ 结尾（20 秒）。

核心要传达的三件事，缺一不可：**能约**、**不会撞**、**有真实迭代记录**。
