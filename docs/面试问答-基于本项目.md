使用说明：每条都是「面试官想听什么 → 怎么回答 → 现场能打开的证据 → 可能的追问」。回答按 60~90 秒设计，别背稿，记住结构就行。

⚠️ 诚实前提：这是**小组模拟团队**完成的项目，不是企业实习。被问到时如实说明"课程里按真实研发流程做的团队项目"，这样反而经得起追问。

## 2. 面对模糊需求，你如何分析并确定核心功能？

**想听什么**：有没有方法，而不是"用户说要什么就做什么"。

**回答（三步）**

> 第一步把需求拆成可验证的句子。原始需求是"能预约座位、不能撞"，我把它拆成七条验收：切换自习室、看到空闲/已约、选时段预约、别人不能再约、能取消、列表区分状态、多人抢只能成功一个。
>
> 第二步找出哪一条决定产品成立。前六条都是界面和流程，第七条"不能撞"才是这个产品的命门——如果两个人能约到同一个座位，其他功能做得再好也没用。所以我把它当第一优先级，并且**把保证放在数据库上**，而不是放在前端按钮状态上。
>
> 第三步写清边界。明确不做的：真实登录、管理员后台、违约惩罚。写进 PRD 的"非目标"，避免做着做着跑偏。

**证据**：PRD 第 2 章「产品目标与非目标」、4 章优先级表、10.1「需求原文 → 实现 → 验证方式」对照表。

**追问：为什么把并发保证放数据库，而不是应用层加锁？**
> 应用层锁只在单进程有效，多进程或以后换部署方式就失效；数据库唯一约束是数据本身的规则，绕不过去。这条主键是「座位 + 日期 + 时段」，一次预约 N 小时就是同一事务写 N 行，任意一行冲突整笔回滚。

## 3. 讲一个你亲自解决过的复杂 Bug

**用 Issue #3「页面切到后台还在每 5 秒轮询」讲，因为过程完整**

**回答**

> **现象**：用户提的 Issue 是"挂着页面不动，服务端日志一直在刷请求"。我一开始以为是正常现象——本来就有 5 秒自动刷新。
>
> **定位**：翻服务端日志，看到从 12:22 到 12:32 连续 10 分钟，每 5 秒固定两条请求（座位图 + 我的预约），期间页面没有任何操作，累计约 240 次。再看前端代码，`setInterval` 只在 `visibilitychange` 时补了一次刷新，**没有在页面隐藏时停掉定时器**——所以标签页切走了还在转。
>
> **修复**：抽出 `startPolling()` / `stopPolling()`，页面隐藏就 `clearInterval` 并把句柄置空，切回前台先刷新一次再重启。特意让 `startPolling` 先停后开，避免切换时出现两个定时器叠加。
>
> **验证**：写了个带 iframe 的探针页，把真实页面放进 375px 视口，覆写 `document.hidden` 触发 `visibilitychange`，用 Performance API 数接口请求：切后台前 2 次，挂 6.5 秒后仍是 2 次，切回前台变 3 次。这才敢说修好了。

**证据**：Issue #3 的研发根因回复、PR #7、PRD 10.3 与 NFR-11。

**追问：为什么不用 `requestIdleCallback` 或 WebSocket？**
> 更合适的方向是 WebSocket 推送，但那要引入连接管理、重连、心跳，对这个规模的本地部署是过度设计；先做最小改动拿到正确性，把推送记进候选需求更合理。

## 4. 你如何定位一个无法直接复现的问题？

**答两个具体手段，比空谈方法论可信**

**回答**

> 两个例子。
>
> 一是 Issue #2 手机窄屏溢出。这类布局问题没法靠"看一眼"判断，我就把页面放进 375px 视口，直接读 DOM 的 `scrollWidth` 和视口宽度比：修复前 8 列固定最小 64px，最小需要约 580px；修复后 `docScrollWidth=360 < 375`，`overflow:false`。把"看起来怪"变成可量化的断言。
>
> 二是 Issue #4 关页面时服务端打印整段异常堆栈。这是偶发的，正常操作很难稳定触发。我用裸 TCP 连接发半截 HTTP 请求，然后 `SO_LINGER` 设为 0 强制 RST，稳定复现 `ConnectionResetError`。修完再跑同样的动作，日志只剩一行"客户端已断开连接"，没有堆栈、没有 500，随后健康检查仍是 200。

**证据**：PRD 10.2 的 TC-23、`tests/test_booking.py` 第 [8] 组用例、Issue #2 与 #4 的修复说明。

**追问：如果连日志都没有？**
> 先想办法制造可观测性——加最小日志或计数，再复现。我这次的 `APP_DEBUG` 开关就是为此加的：只在排查时打印未预期异常的类型，默认不污染日志。

## 5. 你如何设计测试用例？

**回答**

> 我按"规则 → 边界 → 并发 → 异常"四层来设计，一共 43 项自动检查。
>
> - **规则层**：正常预约、取消、列表状态。
> - **边界层**：过去日期、超出 7 天窗口、时段倒序、时段越界、学号非法、座位不存在——都要返回 4xx 且不产生脏数据。
> - **并发层**：16 个线程用 Barrier 同时提交同一座位同一时段，断言恰好 1 个 201、15 个 409，并回查数据库该时段只有 1 条占用。
> - **异常层**：客户端中途断开、目录穿越（`/../server.py` 必须拒绝）、favicon 路由。

**证据**：`tests/test_booking.py`，以及 README 里的手工验证步骤（双窗口抢座）。

**追问：怎么保证断言不是"假通过"？**
> 用例都跑在临时数据库和独立端口上，每次从零建库，避免历史数据掩盖问题；并发用例不看返回体文案，直接回查数据库占用行数。

## 6. 你如何判断一个问题是缺陷还是需求问题？

**用 Issue #6 讲，最能体现判断力**

**回答**

> 用户报"可以一次把座位从早 8 点约到晚 10 点"。这不是代码写错——代码严格按 PRD 实现，PRD 里只写了"选择连续时段"，没规定上限。所以我判定为**需求遗漏**，不是 Bug。
>
> 处理方式也不同于 Bug：Bug 我直接修；这个我没有拍脑袋加上限，因为上限设成 2 小时还是 4 小时、要不要区分高峰、每天最多几次，都会改变产品规则，需要产品和使用者确认。我把它写进 PRD 附录 13.4 作为待定需求，标注"已确认需求，待确认规则后进入 v1.2"，避免它变成口头待办最后被忘掉。

**证据**：Issue #6、PRD 13.4。

**追问：那你会怎么定这个上限？**
> 我会先看真实使用行为：如果多数预约集中在 2~4 小时，就把单次上限设 4 小时、每天最多 2 次；同时保留"续约"能力，让连续自习的需求也能满足。规则确定后再写进 PRD 并补测试。

## 7. 你如何保证修复 Bug 后不引入新问题？

**回答**

> 三层。
>
> 1. **最小改动**：本次四个修复只碰 `server.py`、`static/`、`tests/`，数据库结构和预约规则完全没动，老数据不需要迁移。
> 2. **补回归用例**：每个修复都留下可重复的检查——favicon 路由 200、异常断开后服务仍可用、窄屏无横向滚动、后台不轮询。这样以后再改，跑一遍就知道有没有踩回去。
> 3. **每次提交前跑全量**：43 项检查全通过才敢开 PR，PR 描述里贴的是真实输出，不是"应该没问题"。

**证据**：PR #7 描述中的验证记录、`tests/test_booking.py`。

**追问：有没有差点翻车的例子？**
> 有。修 Issue #4 时我一开始只改了 `do_POST` 的异常处理，重新复现发现日志里还留着 500。查下去才知道 `do_GET` 有自己的一份兜底 `except`，是两处重复代码——后来两处都补上，并把重复的错误响应收敛成同一套处理。

## 8. 团队对优先级意见不一致时，你怎么处理？

**回答**

> 我们 5 个 Issue 的判定标准是"会不会让核心场景走不通"：手机端座位图溢出（P1，手机是主要使用场景）、后台无意义轮询（P1，多人挂页面时请求线性增长）；日志噪音（P2，不影响功能但会掩盖真实故障）；favicon（P3，纯观感）。分歧通常出在"影响人数"和"影响程度"哪个更重要，我的处理是把判断依据写进 Issue 的 Triage 结论里，大家对着同一套理由讨论，而不是各说各的优先级。
>
> 最难的是 Issue #6：用户觉得"这必须马上改"，但从流程上它要先定规则。我的做法是**先承认问题成立**，说清为什么不当场改（会改产品规则），给出明确去向（PRD 13.4 → v1.2），而不是简单说"下个版本再说"。

**证据**：Issue #2~#6 的 Triage 评论。

## 9. 你如何使用 Git 和 GitHub 协作？

**回答**

> 分支按用途分：`main` 只接评审过的 PR，`feature/*` 做功能，`fix/*` 修缺陷，`docs/*` 改文档。每个改动一个分支、一个 PR，PR 描述固定写三件事：改了什么、为什么这么改、怎么验证的；关联 Issue 用 `Fixes #12`，合并时自动关闭。
>
> 发布用 tag 加 Release，Release Notes 写清新增功能与修复项，用户可以直接按版本验证。仓库里还放了 Issue 模板（Bug / 体验问题）和 CONTRIBUTING，把"复现步骤、预期、实际、截图日志"这些要求固化下来。

**证据**：`CONTRIBUTING.md`、`.github/ISSUE_TEMPLATE/`、三次 PR 与两次 Release。

**追问：有没有用过 rebase / cherry-pick？**
> 这个项目用的是合并提交，保持每条 PR 的历史可见；如果团队约定线性历史，我会在合并前 rebase 到最新 main 并重跑测试，避免把半成品提交带进去。

## 10. 你如何判断 AI 生成的代码是否可靠？

**这是这套流程里最值得讲的一题**

**回答**

> 我的判断顺序是：先看它有没有把"正确性"放在能验证的地方，再看它给不给得出证据。
>
> 具体到这次：AI 写并发逻辑时最省事的做法是在应用层加锁或查一次再插入——这两种在并发下都会漏。我要求最终实现必须让数据库主键承担唯一性，然后**不看它说"已完成"，只认 43 项检查的输出和 16 并发只成功 1 个的实测**。
>
> 还有一类是它容易"编"的地方：报错信息、接口字段、日志格式。这次就踩到过——我让它总结验证结论时，它把实测数字写成了想当然的版本，我用脚本重跑才发现对不上。所以凡是数字、状态码、命令输出，我都要求现场跑一遍再写进文档。

**证据**：PRD 10.3 里贴的是真实运行输出；PR #7 的验证记录同样来自实测。

**追问：那你怎么用 AI 提效又不失控？**
> 把它当执行力很强但需要验收的同事：需求边界、验收标准、测试用例我来定，代码和重复性工作它来写，最后用测试和实测数据当验收关卡。不通过就不算完成。

## 11. 项目经历过哪些迭代？怎么衡量一次迭代有没有价值？

**回答**

> 两次发布。v1.0.0 是第一版全功能交付；v1.1.0 是修 4 个用户实测问题加 PRD 升到 V1.1。衡量标准不看"改了多少行"，看三件事：核心场景是否更顺畅（手机端从不可用到可用）、无效开销是否下降（后台标签页从持续轮询到零请求）、可维护性是否提升（日志噪音消除，故障可辨识）。

**证据**：两个 Release 的 Notes 对比、PRD 修订记录的 V1.1 条目。

## 12. 如果并发量再大 100 倍，你的设计还成立吗？

**回答**

> 并发正确性还成立——唯一约束不随量变化。瓶颈会换地方：SQLite 单写者，写入会排队。真到这个量级我会做三件事：把库换成 PostgreSQL 并保留同样的唯一约束（约束语义不变，迁移成本主要在连接层）；轮询改成 WebSocket 或 SSE 推送，把请求量从"人数 × 频率"降到"事件驱动"；座位图接口加短时缓存，读多写少的部分不必每次穿透数据库。
>
> 但我会先确认量级是否真到这一步——这个系统的实际场景是单校区，几十人同时在线，提前上分布式是把复杂度换成了维护成本。

**追问：那你为什么不用 PostgreSQL 一步到位？**
> 因为这个产品的约束条件是"零依赖、能本地一条命令跑起来"，评审和使用者要能自己启动。这是我在 PRD 里写明的非功能需求，不是技术偏好。

## 13. 这个项目有什么不足？

**主动说，比被问出来强**

**回答**

> 三条最实在的：
>
> 1. **身份没有鉴权**。学号只是归属标识，知道别人学号就能替他取消预约。PRD 里明确写成非目标，但真实上线必须先解决，方案是校园统一认证加服务端会话。
> 2. **前端没有自动化测试**。窄屏布局和轮询暂停这两项是靠无头浏览器脚本验证的，脚本没入库，属于一次性检查。这块应该补成正式的端到端用例。
> 3. **预约规则还太宽松**。就是 Issue #6，没有时长上限。

**证据**：PRD 2.2（非目标）、13.3（候选需求）、13.4（已知问题）。
